What you should know
  • A descriptor in non-blocking mode (O_NONBLOCK, set with fcntl; Go: syscall.SetNonblock) never puts the program to sleep.
  • A call that would have to wait fails at once with EAGAIN, "try again". A write that can take only part of the bytes returns a short count.
  • The program can do something else and ask later. But asking blindly, again and again, either wastes CPU or answers late.
Who uses it

Servers that handle thousands of connections cannot afford one sleeping thread per connection. They put every socket in non-blocking mode and ask the kernel, in one call, which ones are ready. The Go runtime does exactly this under your goroutines: on a real Linux machine, every socket of a Go program is non-blocking, and a goroutine that "blocks" in Read is parked by the runtime, not by the kernel. These machines run Go's network code in blocking mode instead, which is simpler to trace.

Run this

peek listens in non-blocking mode and asks every second. Build it and trace its accept and read calls on B:

 $ strace -e trace=fcntl,accept,read peek

A connects after 3 seconds and sends one line:

$ sleep 3; echo hello | nc -N $B_IP 9000

What you should notice

  • fcntl(3, F_SETFL, O_RDWR|O_NONBLOCK): that is SetNonblock.
  • Each accept(3, …) = -1 EAGAIN returned at once, and peek printed "nobody yet".
  • Then the connection, the line, and read returning 0.
