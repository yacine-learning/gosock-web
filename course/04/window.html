What you should know
  • Every segment carries the sender's receive window: the free room in its receive buffer. The other side never sends more than that.
  • A program that does not read lets its receive buffer fill; the window falls to 0 and the sender stops. Its send buffer fills too, and then its write (or sendfile) sleeps.
  • This is flow control: the slowest reader sets the pace, end to end, with no message saying "slow down".
Restarting after a zero window

When the reader drains its buffer, its kernel sends an ACK with the new, larger window (a "window update") and the sender resumes. If that update were lost, both sides would wait for ever, so a sender facing a zero window sends a small probe now and then; the answer carries the current window.

The default buffers here are 128 KB to receive and 85 KB to send. Real Linux grows them automatically for fast, distant peers (up to several MB), unless the program set them with setsockopt.

Run this

slowrecv accepts one connection, then waits 8 seconds before reading anything. Build it, start it on B, send the big file from A, and look at both sockets while B is not reading:

 $ slowrecv & $ gosock send $B_IP:9000 /tmp/big.bin & $ ss -tni $ ss -tn

What you should notice

  • On B, Recv-Q is 131072: the receive buffer is full. On A, Send-Q is 87040 and snd_wnd:0.
  • The kernel view shows A's gosock asleep in sendfile, and both bars full.
  • After 8 seconds B reads, the window opens, and the rest of the 2 MB flows.
