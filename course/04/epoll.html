What you should know
  • epoll waits for many descriptors at once: register each one with epoll_ctl, then epoll_wait sleeps until one or more are ready and returns that list.
  • One thread, one loop: serve exactly the ready descriptors, never block on one. A slow client costs nothing while it is silent.
  • This is how Nginx, Redis, Node.js and the Go runtime serve thousands of connections.
Ready, level-triggered, and the Go runtime

"Ready" means a call would not wait: a listener has a connection to accept, a socket has data (or the end) to read, or room to write. By default epoll is level-triggered: a descriptor is reported at every epoll_wait while it stays ready. With EPOLLET (edge-triggered, not modelled here) it is reported once per change, and the program must read until EAGAIN.

The Go runtime's "netpoller" is such a loop. When a goroutine's Read finds no data, the runtime registers the socket, parks the goroutine, and runs others; when epoll_wait reports the socket, the goroutine is woken. You write simple blocking code; the runtime turns it into this.

epoll in simplified kernel C struct eventpoll { // one per epoll_create1(): another descriptor struct rb_root rbr; // the registered descriptors (epoll_ctl) struct list_head rdllist; // the READY ones wait_queue_head_t wq; // processes sleeping in epoll_wait }; // when data arrives on a socket, its wake-up callback runs: void ep_poll_callback(struct epitem *epi) { list_add_tail(&epi->rdllink, &epi->ep->rdllist); // now ready wake_up(&epi->ep->wq); // wake epoll_wait } // epoll_wait copies rdllist to user space: the cost depends on how many are // READY, not on how many are registered. That is the whole trick.

Run this

epollsrv serves port 9000 with one epoll loop. Build it and start it on B, traced to a file:

 $ strace -o ep.trace epollsrv &

Client 1 connects and stays silent for 4 seconds; client 2 says hello meanwhile:

$ sleep 4 | nc -N $B_IP 9000 & $ echo hello | nc -N $B_IP 9000

After 4 seconds, look at what the loop did:

$ grep -c epoll_wait ep.trace $ grep epoll_ctl ep.trace $ pkill epollsrv

What you should notice

  • Client 2 was served at once although client 1 was connected and silent: "[6] hello", "[6] closed", then "[5] closed" 4 seconds later. (3 is the listener, 4 the epoll instance itself.)
  • One process, no thread per client: a few epoll_wait calls, one per burst of events.
