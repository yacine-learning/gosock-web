By the end of this course you will be able to explain, with commands you ran yourself, what the Linux kernel does when a program sends a file to another machine.

The whole trip

This is what happens when a file is sent. You do not need to understand it yet. Press play once, and come back to it whenever you feel lost: every lesson explains one part of it.

Your two machines

The right half of this page is your lab: two Linux machines, A and B, joined by one cable. Each has its own kernel, its own files and its own terminal. Type in a terminal, or press run next to a command here:

$ hostname $ ls -l /tmp $ hostname $ ls -l /tmp $ ping -c 2 $A_IP

What you should notice

  • A and B really are separate: /tmp/big.bin exists on A and not on B. Getting it across is the job of this module.
  • Above the terminals, each machine shows its user space (running programs) and its kernel (sockets). Both are empty for now: a command like ls is gone before you can see it.
  • $A_IP and $B_IP hold the machines' addresses, so no page ever makes you type one.
What is real here, and what is simulated

Real: the Go compiler (the official one, running in your browser) and the programs you will write with it.

Simulated: the two machines. Their kernels are a model written for this course: files, descriptors, sockets and TCP behave like Linux in the ways the lessons use. The commands (nc, strace, ss…) are small versions of the real ones, with the options the course needs.

Where the ideas come from

I borrowed ideas, not material, from teachers whose courses are worth knowing: Stanford CS144 (Keith Winstein, Nick McKeown) for building one real thing, judged by tests; MIT 6.S081 (Frans Kaashoek, Robert Morris) for looking inside the kernel; CMU 15-213 (Randal Bryant, David O'Hallaron) for debugging with nothing but tools; OSTEP (Remzi and Andrea Arpaci-Dusseau) for starting from the problem; Eric Mazur (Harvard) for guessing before seeing; Kurose and Ross for learning networking top-down: see it work first, then open the box.
