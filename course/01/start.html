What you should know
  • At the end you will explain, with commands you ran yourself, what the Linux kernel does when a file is sent to another machine.
  • The right half of the page is your lab: two Linux machines, A and B, each with its own kernel, files and terminal.
  • A program cannot touch a disk or a network card. It asks the kernel, through a system call.
What a system call is, and the whole trip

Your program runs in user space: it can only touch its own memory. Everything else (files, the network, other programs) belongs to the kernel. A system call is the one door between the two: the program puts a number and some arguments in CPU registers, executes a special instruction, and the CPU switches to kernel mode. The kernel does the work and returns a number: a result, or a negative error code.

What is real here, and what is simulated

Real: the Go compiler (the official one, running in your browser) and the programs you will write with it.

Simulated: the two machines. Their kernels are a model written for this course: files, descriptors, sockets and TCP behave like Linux in the ways the lessons use. The commands (nc, strace, ss…) are small versions of the real ones, with the options the course needs.

Run this

Type in a terminal, or press run:

$ hostname $ ls -l /tmp $ hostname $ ls -l /tmp $ ping -c 2 $A_IP

What you should notice

  • /tmp/big.bin exists on A and not on B. Getting it across is the job of this module.
  • Above the terminals each machine shows its user space (programs) and its kernel (sockets). Both stay empty: ls is gone before you can see it.
  • $A_IP and $B_IP hold the addresses, so you never type one.
