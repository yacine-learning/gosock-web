Trace your own gosock on both machines, and find out what the kernel was really asked.
What you should know
  • The same io.Copy line does not make the same system calls on both ends.
  • Sending a file to a TCP connection, Go asks the kernel for a shortcut, sendfile: the bytes go from the file to the socket without passing through your program.
  • Receiving, every chunk goes through your program: a read from the socket, then a write to the file.
On a real Linux machine

The sender's trace looks like this one, with extra lines from Go's runtime (threads, timers) and several sendfile calls instead of one. The receiver differs: there Go also finds a shortcut, a pair of splice calls through a pipe. This simulator's receiver takes the plain road, which is the one worth understanding first.

sendfile in simplified kernel C // sendfile(out_fd = 4 the socket, in_fd = 3 the file, NULL, count) ssize_t sys_sendfile(int out_fd, int in_fd, loff_t *offset, size_t count) { struct file *in = current->files->fd[in_fd]; struct file *out = current->files->fd[out_fd]; // pages of the file (already in kernel memory) are handed to the socket: // no copy into the program's memory and back return do_splice_direct(in, &in->f_pos, out, count); }

Compare with the receiver: each read copies kernel → program, each write copies program → kernel. Two copies and two system calls per chunk.

Run this

Record what both ends ask the kernel (-o writes the trace to a file):

$ strace -o recv.trace gosock recv :9000 in.bin $ strace -o send.trace gosock send $B_IP:9000 /tmp/big.bin

How many read and write calls carried the 2 MB? (grep -c counts lines.)

$ grep -c 'read(' send.trace $ grep -c 'write(' send.trace $ grep sendfile send.trace $ grep -c 'read(' recv.trace $ grep -c 'write(' recv.trace

What you should notice

  • On A: no read, one write (the sent 2097152 bytes line). The file travelled in sendfile(4, 3, …).
  • You never wrote sendfile: Go chose it.
  • On B: dozens of read and write pairs.
