Send a 2 MB file from A to B with nc, prove it arrived intact, and meet your first real networking surprise.

nc (netcat) opens or accepts one TCP connection and joins it to its own input and output. With shell redirections (> and <) that is a file transfer. sha256sum prints a fingerprint of a file: same fingerprint, same bytes.

$ sha256sum /tmp/big.bin B will run nc -l 9000 > in.bin (wait for a connection, store what arrives). A will run nc $B_IP 9000 < /tmp/big.bin (connect, send the file). A's nc reads the last byte of the file and sends it. What happens next? Both nc commands exit by themselves and the file is complete. The whole file arrives, but at least one nc never exits. Only part of the file arrives, because 2 MB is more than one connection carries. A's nc exits with an error when it runs out of file.

The file arrives complete, but nothing tells the receiver that it has ended. Run it, then watch the animation at the bottom.

B waits for a connection:

$ nc -l 9000 > in.bin

A sends the file. timeout 5 kills nc after 5 seconds in case it does not stop; exit status 0 means it finished by itself, 124 means timeout had to kill it:

$ timeout 5 nc $B_IP 9000 < /tmp/big.bin; echo "exit $?"

Is the file on B complete?

$ sha256sum in.bin

Now the fix: -N makes nc shut down its sending side when its input ends.

$ nc -l 9000 > in2.bin $ nc -N $B_IP 9000 < /tmp/big.bin; echo "exit $?" $ sha256sum in2.bin

What you should notice

  • The first run ended with status 124, yet the fingerprint on B matches the original. The data was never the problem. The end was.
  • The second run ended by itself with status 0, on both machines.
  • While nc -l waits, B's kernel shows a socket in state LISTEN. It is gone when nc exits.
