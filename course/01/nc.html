Send a 2 MB file from A to B with nc, prove it arrived intact, and meet your first networking surprise.
What you should know
  • nc (netcat) opens or accepts one TCP connection and joins it to its input and output. With < and > that is a file transfer.
  • sha256sum prints a fingerprint: same fingerprint, same bytes.
  • Sending the last byte does not end a connection. The receiver only learns "that's all" when the sender closes its side (a FIN).
Why the receiver cannot guess the end

TCP carries a stream of bytes with no built-in "end of file" marker. A pause is not an end: more bytes could arrive one second or one hour later. So the receiving program keeps calling read, and read keeps waiting, until the other side says explicitly that it will send nothing more. That signal is a FIN segment, sent by the kernel when the sender closes the connection or shuts down its sending side. Then read returns 0, which every program treats as "end".

Plain nc does not close its sending side when its input ends: it keeps the connection open in case the other side sends something back. -N changes that.

Run this

$ sha256sum /tmp/big.bin B will run nc -l 9000 > in.bin (wait, store what arrives). A will run nc $B_IP 9000 < /tmp/big.bin (connect, send the file). A's nc sends the last byte. What happens next? Both nc commands exit by themselves and the file is complete. The whole file arrives, but at least one nc never exits. Only part of the file arrives, because 2 MB is more than one connection carries. A's nc exits with an error when it runs out of file.

The file arrives complete, but nothing tells the receiver that it has ended.

 $ nc -l 9000 > in.bin

timeout 5 kills nc after 5 s; status 124 means it had to:

$ timeout 5 nc $B_IP 9000 < /tmp/big.bin; echo "exit $?" $ sha256sum in.bin

Now with -N: close the sending side when the input ends.

$ nc -l 9000 > in2.bin $ nc -N $B_IP 9000 < /tmp/big.bin; echo "exit $?" $ sha256sum in2.bin

What you should notice

  • The first run ended with 124, yet B's fingerprint matches. The data was never the problem; the end was.
  • The second run ended by itself with 0, on both machines.
  • While nc -l waits, B's kernel shows a socket in state LISTEN.
