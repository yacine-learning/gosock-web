Every trace is full of small numbers: openat(…) = 3, read(3, …). This page answers one question properly: what is a file descriptor, exactly?

The problem it solves

Reading a file takes many system calls: open it, read a bit, read more, close it. Between those calls the kernel must remember which file, how far you have read, and whether you may write. So the kernel keeps the object itself and gives your program a handle: a small number. That number is the file descriptor.

Every process has its own table, kept by the kernel. A file descriptor is the slot number in that table. Each slot points to an open file description, which says what the thing is and where you are in it.

Look at a live one

The kernel view of your machines shows each process's table. Start your receiver on B and leave it waiting:

$ gosock recv :9000 big.copy

Look at B's user space: descriptors 0 1 2 lead to the terminal, and 3 to the listening socket. Now set Wire to slow and send:

$ gosock send $B_IP:9000 /tmp/big.bin

What you should notice

  • On B, two slots appeared: 4, the connection that Accept returned, and 5, the file that os.Create made. The kernel always hands out the lowest free number.
  • The file's offset moves as bytes are written. It lives in the open file description, not in the number and not in the file.
  • A has its own 3 and 4, and they are different things (a file, a socket). Descriptor numbers mean something only inside one process.
  • When a program exits, its table is emptied: every slot is closed for it.
The same thing in simplified kernel C

These are the real kernel structures with most fields removed:

struct files_struct { // one per process: the fd table struct file *fd[NR_OPEN]; // fd[3] is "file descriptor 3" }; struct file { // the open file description loff_t f_pos; // the offset: the next read/write starts here unsigned f_flags; // read-only, append, ... const struct file_operations *f_op; // read, write, close... for THIS kind of object struct inode *f_inode; // the file (for a socket: the socket's inode) }; // read(3, buf, n) in the kernel, roughly: // struct file *f = current->files->fd[3]; // return f->f_op->read(f, buf, n, &f->f_pos);

Look at the last line. The same read works on a file, a socket and a pipe because each open file description carries its own table of operations (f_op). That is why io.Copy could copy between a file and a connection: to the kernel both are file descriptors.
