syscall.Open("/nope", syscall.O_RDONLY, 0) fails. What does the kernel send back? The text "no such file or directory". A descriptor that is not usable. A negative number: minus the error code, 2 (ENOENT). Nothing: Go checks that the file exists before asking.

The kernel returns -2; Go turns it into -1 and syscall.Errno(2), whose text comes from a table in the program.

 You call syscall.Read(fd, buf) on a socket with a 64 KB buffer. It returns 1460. What does that mean? 1460 bytes had arrived; more may come. Read again. The sender sent exactly 1460 bytes. An error: a read must fill the buffer. The connection is closing.

A read returns what is there now, up to the buffer's size. Only 0 means the end.

 syscall.Write(fd, b) returns n < len(b) and no error. What should the program do? Nothing: the kernel will write the rest by itself. Report an error. Write all of b again. Write b[n:], and repeat until nothing is left.

The kernel took n bytes; the rest is still yours. That is writeAll.

 c := syscall.Dup(a), then you read 5 bytes from c. Where does the next read from a start? At byte 0: each descriptor has its own offset. At byte 5: a and c point to the same open file description, and share its offset. At the end of the file. It fails: a file cannot be read through two descriptors.

dup makes a second slot for the same open file description, and the offset lives there.

 Why is the second cat of a 2 MB file much faster than the first? The first cat left its buffer in memory for the next one. The disk remembers the last file read. The kernel kept the file's pages in the page cache: the second read is a memory copy. The second cat used sendfile.

The first read was a miss for every page and waited for the disk; the pages stayed in the page cache.

 write to a file returned. Is the data on the disk? Not necessarily: it is in the page cache, dirty, and reaches the disk later (or at fsync). Yes: write returns when the disk confirms. Only if the file is smaller than 4 KB. No, it is only in your program's buffer.

The kernel has it; the disk will have it after writeback, sync or fsync.

 A program fails with EMFILE, "too many open files". What is the most likely bug? The disk is full. Another program has the file open. The file is too large. Descriptors opened and never closed, until the process reached its limit.

Each process may hold a limited number of descriptors (1024 by default); a missing Close uses them up.

 Copying 2 MB to a 1 MB disk, the last calls are write(…, 65536) = 45056, then write(…, 20480) = -1 ENOSPC. What did the program do right? It used a 64 KB buffer. After the short write, it tried to write the 20480 bytes left, and got the real error. It wrote a new chunk after the short write. Nothing: it should have stopped at the short write.

65536 − 45056 = 20480: it wrote exactly what was left, so the error it reports is the true one, with no byte silently dropped.
