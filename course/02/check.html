What is a file descriptor? The number of the file on the disk (its inode number). A slot number in a table the kernel keeps for each process. The position in the file where the next read starts. A number shared by every process that opens the same file.

The kernel keeps one table per process; the descriptor is the index. The position (the offset) lives in the open file description the slot points to, not in the number.

 On this course's machines, a program opens its first file. Which descriptor does it get? 013It depends on the file's name.

0, 1 and 2 are standard input, output and error, and the kernel always gives the lowest free number: 3.

 Plain nc sent the whole file, yet the receiving nc never exited. Why? Nothing told the receiver the stream had ended: the sender never closed its sending side. The last segment was lost and had to be sent again. The receiver's buffer was full. TCP needs an explicit message saying how long the file is.

TCP has no "end of file" inside the data. The end is a FIN, sent when the sender closes (or shuts down) its side; -N made nc do that.

 read on a socket returns 0. What does it mean? No data has arrived yet; try again. An error; look at errno. The buffer you gave was too small. The other side closed: there will be no more data.

0 means end of stream (end of file, for a file). A read with no data yet does not return: it waits.

 A server made with net.Listen has accepted one client. How many sockets does it hold? One: the client's connection replaced the listener. Two: the listening socket, and a new one for the connection. Three: listening, sending and receiving. None: sockets belong to the kernel, not to the program.

Accept returns a new socket (a new descriptor) for each connection; the listening socket keeps listening.

 Tracing gosock send, the 2 MB of the file went to the kernel through… many read and write pairs. one big write. sendfile, from the file's descriptor to the socket's, without passing through the program. splice through a pipe.

Go saw a file going to a TCP connection and asked for sendfile. The receiving side, in this simulator, used read and write pairs.

 What does defer f.Close() do? It closes f when the surrounding function returns, whichever way it returns. It closes f right now, but lets the program continue. It closes f when the program exits. It closes f only if an error happened.

A deferred call runs when the function returns, on every path: a normal return or an error return.

 The kernel view shows gosock recv "in the kernel, inside accept". What is the program doing? Checking for a connection again and again, using the CPU. Running kernel code by itself. It has crashed and the kernel holds what is left. Sleeping in a system call; the kernel wakes it when a connection is ready.

A blocking call puts the program to sleep inside the kernel. No CPU is used until the kernel has something to return.
