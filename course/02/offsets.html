What you should know
  • The offset (where the next read or write starts) lives in the open file description, not in the descriptor and not in the file.
  • Opening a file twice gives two descriptions: two independent offsets. dup gives a second number for the same description: one shared offset.
  • lseek (syscall.Seek) moves an offset; pread reads at a position without moving it.
Where sharing matters

A shell running cmd > log 2>&1 opens log once and makes descriptor 2 a duplicate of 1. Both share one offset, so the program's output and errors land one after the other instead of overwriting each other. A child process created by fork also shares its parent's descriptions: that is how a shell passes a terminal to every command.

Two processes that each open the same file have separate offsets and can overwrite each other's bytes, unless they open it with O_APPEND, which moves the offset to the end before every write.

The offset in simplified kernel C struct file { // one per open(): the open file description loff_t f_pos; // THE offset unsigned f_flags; // O_RDONLY, O_APPEND, O_NONBLOCK... atomic_long_t f_count; // how many descriptors point here (dup adds one) struct inode *f_inode; // the file }; int sys_dup(int oldfd) { // a new slot, the same struct file struct file *f = current->files->fd[oldfd]; atomic_long_inc(&f->f_count); return install_lowest_free_fd(f); } off_t sys_lseek(int fd, off_t off, int whence) { struct file *f = current->files->fd[fd]; f->f_pos = (whence == SEEK_SET ? 0 : whence == SEEK_CUR ? f->f_pos : i_size(f->f_inode)) + off; return f->f_pos; }

 $ offsets

What you should notice

  • b starts again at "hello": its own offset. c continues where a stopped: " from".
  • Moving c back to 0 moved a too.
  • In the kernel view, descriptors 3 and 5 always show the same offset.
