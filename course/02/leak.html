A bug on purpose: a program that opens files and never closes them.
What you should know
  • A process may hold a limited number of descriptors: 1024 by default on Linux (ulimit -n).
  • Past the limit, open, socket and accept fail with EMFILE, "too many open files".
  • A forgotten Close is invisible at first: each leak costs one slot, and the program fails much later, far from the bug.
Why there is a limit, and why servers hit it

Every slot points to kernel memory (an open file description, perhaps a socket with its buffers). The limit stops one program from eating the kernel's memory. It can be raised (ulimit -n, or LimitNOFILE for a service), and busy servers do raise it, because each client connection is one descriptor.

That is also why the bug is common in servers: one connection handled without closing it is one descriptor gone. Under real traffic the server runs out after a few hours, and starts refusing everyone with an error that points at accept, not at the missing Close.

Run this

leak opens /etc/hostname in a loop and keeps every file. Build it, run it, then look at the end of its trace:

 $ leak $ strace -o leak.trace leak $ grep -c openat leak.trace $ grep EMFILE leak.trace $ tail -n 3 leak.trace

What you should notice

  • Open number 1022 failed: descriptors 3 to 1023 were taken (0, 1, 2 were already in use).
  • The last openat returned -1 EMFILE (Too many open files); then the program printed it and exited.
  • Nothing failed before that: the bug was there from the first open.
